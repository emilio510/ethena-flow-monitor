## Recursion score made UTILIZATION-AWARE (2026-06-16, commits c265877 + 328f524, deployed to prod)

## Flow tracker feature (shipped 2026-05-28, merged to main)
Daily tracker of ≥$1M outflows from Ethena's monitored XRPL+EVM wallets. Code in `lib/flows/*` (fetch-only: XRPL JSON-RPC + Alchemy JSON-RPC, no viem/server-only so it runs under both `tsx` and vitest). Pipeline: scan → classify (redeem/rebalance/external + high/low confidence) → probe destination holdings → merge/prune (90-day rolling) → promote. Runs in the daily launchd job via `scripts/refresh-flows.ts` (`npm run refresh:flows`, needs ALCHEMY_KEY in .env.local), commits `data/ethena-flows.json` (~783KB, ~1930 flows) + `data/ethena-discovered-wallets.json`. Dashboard renders a capped recent-flows table (100 rows + per-class counts). Spec/plan in `docs/superpowers/{specs,plans}/2026-05-28-ethena-flow-tracker*`.
**Quarantine guarantee (load-bearing):** scanners read `buildScanSet` (config wallets + discovered); backing readers (`getEthenaRlusdHoldings`, `balances.ts`) read config ONLY. A discovered/quarantined wallet can never reach the backing total without a human editing `config/`. Don't wire discovered wallets into backing readers.
**Two known v1 limitations (non-blocking, good follow-ups):** (1) `probeEvm` only queries the 5 Ethena stables, so it can't see a *foreign* token — EVM destinations holding any stable read as rebalance/low even if they're exchanges; EVM rebalance-vs-external labels are soft (XRPL single-trustline is the only high-confidence new-address signal, so EVM never auto-promotes — safe but the heuristic is half-blind). Fixing needs full-token-set probe + spam-token filtering (this is the `classifyNewAddress` domain seam Emile may want to own). (2) a total RPC outage logs per-chain warnings but the script still exits "ok".
